# Практика 11 — JWT для API и OAuth через GitHub

## Цель работы

Реализовать в проекте Boardy два механизма:

1. JWT-авторизацию для связки `PHP → React → FastAPI`
2. OAuth-вход через GitHub

В результате сайт должен:
- уметь выдавать JWT по активной PHP-сессии
- передавать JWT в FastAPI через `Authorization: Bearer ...`
- создавать комментарии от имени пользователя из токена
- поддерживать вход через GitHub без отдельной регистрации пароля

---

## Исходные данные

Проект развернут на домене:

- сайт: `https://belyaevubuntu.ru`
- API: `https://api.belyaevubuntu.ru`

До начала практики уже работали:

- PHP-сессии
- регистрация и логин
- `messages.php`, `submit.php`, `logout.php`
- React-страница комментариев
- FastAPI API для комментариев

# Часть A. JWT для API

## 1. Зачем понадобился JWT

PHP и FastAPI работают как два разных сервиса:

- `belyaevubuntu.ru` — PHP, HTML, куки, сессии
- `api.belyaevubuntu.ru` — FastAPI, JSON API

PHP знает пользователя через `$_SESSION`, но FastAPI напрямую PHP-сессии не читает.  
React, который находится на основном сайте, может узнать пользователя через PHP, получить токен и уже этот токен передать в FastAPI.

Поэтому была реализована схема:

`login/register/OAuth -> $_SESSION -> /api/me.php -> JWT -> React -> Authorization: Bearer -> FastAPI`

---

## 2. Файл `auth.py`

В FastAPI был создан файл `auth.py` с функцией `get_current_user`, которая:

- читает заголовок `Authorization`
- проверяет, что он начинается с `Bearer `
- извлекает сам JWT
- декодирует его через `jwt.decode(...)`
- возвращает payload
- отдаёт `401`, если токен отсутствует, истёк или невалиден

Это позволило убрать анонимный доступ к изменяющим endpoint API.

**Скриншот:** `01-no-token.png`

---

## 3. Что означает `Bearer` в заголовке `Authorization`

`Bearer` — это тип схемы авторизации.

Заголовок:

```http
Authorization: Bearer <token>
```

означает: «я передаю bearer-token, то есть токен-предъявитель».  
Сервер ожидает не просто строку, а конкретный формат заголовка.

### Почему не просто `Authorization: eyJ...`?

Потому что без схемы `Bearer` серверу пришлось бы гадать, что именно пришло в заголовке:

- JWT
- Basic auth
- API key
- что-то кастомное

`Bearer` делает формат запроса явным и стандартным.

---

## 4. Файл `/api/me.php`

Был создан PHP-endpoint `/api/me.php`, который:

1. запускает сессию через `session_start()`
2. проверяет, есть ли `$_SESSION['user_id']`
3. если пользователь не залогинен — возвращает `401`
4. если пользователь есть — генерирует JWT
5. отдаёт JSON вида:

```json
{"token":"eyJ..."}
```

**Скриншот:** `02-me-php.png`

---

## 5. Почему `me.php` использует `session_start()`, а не принимает логин/пароль

`me.php` не должен заново логинить пользователя.

Его задача — взять уже существующую авторизацию из PHP-сессии и выдать React короткоживущий JWT для API.

Если бы `me.php` принимал логин/пароль:

- пришлось бы передавать пароль ещё раз
- React знал бы пароль пользователя
- логика логина дублировалась бы

Правильнее использовать уже существующую серверную сессию.

---

## 6. Роль куки `PHPSESSID` в запросе к `me.php`

Кука `PHPSESSID` нужна, чтобы PHP понял, **какую именно сессию открыть**.

Сценарий такой:

1. браузер делает запрос к `/api/me.php`
2. вместе с запросом уходит `Cookie: PHPSESSID=...`
3. `session_start()` по этой куке находит файл сессии
4. PHP восстанавливает `$_SESSION`
5. по `$_SESSION['user_id']` и `$_SESSION['user_name']` создаётся JWT

То есть `PHPSESSID` — это ключ к серверной сессии, а не сам токен авторизации для FastAPI.

В итоге комментарий создаётся от имени реального пользователя, а не от фиктивного автора.

## 10. Проверка JWT на jwt.io

JWT был вставлен на jwt.io.  
Были видны:

- `header`
- `payload`
- `Signature Verified`

**Скриншот:** `06-jwt-io.png`

### Payload зашифрован или закодирован?

Payload **не зашифрован**, а **закодирован** в Base64URL.

Это значит, что любой, кто получит токен, может прочитать payload и увидеть, например:

- `user_id`
- `name`
- `exp`

### Что увидит злоумышленник, если перехватит токен?

Он увидит содержимое payload:

- ID пользователя
- имя
- срок жизни токена

### Почему это не считается проблемой?

Потому что безопасность JWT не в сокрытии payload, а в **подписи**.

Злоумышленник может прочитать токен, но не может:

- незаметно поменять `user_id`
- продлить `exp`
- подделать подпись без секретного ключа

То есть JWT читается, но не должен модифицироваться без секрета.

## 15. Почему ищем пользователя по `github_id`, а не по email

Искать по `github_id` правильнее, чем по email, по нескольким причинам:

1. `github_id` — это стабильный внешний идентификатор аккаунта GitHub
2. email на GitHub может быть:
   - скрыт
   - недоступен
   - изменён
3. у разных провайдеров могут быть одинаковые или конфликтующие email-сценарии
4. внешний ID — это canonical key для OAuth-провайдера

Поэтому при OAuth-логине правильный путь такой:

- пришёл профиль GitHub
- берём `profile['id']`
- ищем `SELECT ... WHERE github_id = ?`

---

## 16. Файл `oauth-github.php`

Этот файл запускает OAuth flow:

1. генерирует случайный `state`
2. сохраняет его в `$_SESSION['oauth_state']`
3. делает redirect пользователя на GitHub

---

## 17. Файл `oauth-callback.php`

Этот файл завершает OAuth flow:

1. проверяет `state`
2. получает `code` из GitHub callback
3. сервер-сервер делает запрос на обмен `code -> access_token`
4. потом получает профиль пользователя через GitHub API
5. ищет пользователя по `github_id`
6. если не найден — создаёт его
7. создаёт локальную PHP-сессию
8. перенаправляет пользователя на `messages.php`

## 21. Полный flow OAuth → JWT → API

После входа через GitHub цепочка работает так:

1. пользователь нажимает кнопку **«Войти через GitHub»**
2. `oauth-github.php` создаёт `state` и редиректит на GitHub
3. GitHub возвращает пользователя в `oauth-callback.php`
4. `oauth-callback.php` получает профиль и создаёт `$_SESSION`
5. пользователь открывает страницу React-комментариев
6. React делает `fetch('/api/me.php', { credentials: 'include' })`
7. `me.php` по `PHPSESSID` открывает сессию и генерирует JWT
8. React получает JWT и сохраняет его в state
9. React делает `fetch` в FastAPI с `Authorization: Bearer <jwt>`
10. FastAPI извлекает `user_id` из payload
11. комментарий создаётся от имени GitHub-пользователя

Именно так OAuth, сессии, JWT и API связываются в одну цепочку.

---

## 22. Что такое `state` в OAuth

`state` — это случайная строка, которая используется как защита от CSRF-атаки в OAuth flow.

Схема такая:

1. до редиректа на GitHub сервер генерирует случайный `state`
2. сохраняет его в `$_SESSION`
3. отправляет этот `state` в запросе на GitHub
4. GitHub возвращает его обратно в callback
5. сервер сравнивает:
   - `$_GET['state']`
   - `$_SESSION['oauth_state']`

Если значения не совпадают — flow должен быть прерван.

---

## 23. Сценарий CSRF-атаки без `state`

Если убрать `state`, возможен такой сценарий:

1. злоумышленник начинает OAuth flow у себя и получает свой `code`
2. он не завершает логин у себя, а сохраняет ссылку с этим `code`
3. потом он отправляет жертве ссылку на:
   `https://belyaevubuntu.ru/oauth-callback.php?code=ATTACKER_CODE`
4. жертва переходит по ссылке, уже находясь на сайте Boardy
5. сервер не проверяет, кто инициировал flow
6. сервер обменивает `code` злоумышленника на `access_token`
7. получает профиль злоумышленника
8. создаёт сессию на сайте **не для жертвы, а для аккаунта злоумышленника**
9. жертва оказывается залогинена под чужим GitHub-аккаунтом

То есть без `state` можно подменить OAuth-результат и навязать жертве чужой вход.

## 26. Сравнение механизмов

| Вопрос | Куки + сессии | JWT | OAuth |
|---|---|---|---|
| Где хранятся данные? | На сервере, в сессии; в браузере только ID сессии | В самом токене на клиенте; подпись проверяется на сервере | У провайдера и частично у клиента/на сервере приложения |
| Кто прикрепляет к запросу? | Обычно браузер автоматически через Cookie | Клиент сам кладёт в `Authorization` | Браузер и сервер участвуют в redirect/back-channel flow |
| Для какого типа клиентов? | SSR, сайты на одном домене | SPA, mobile, API-клиенты, межсервисное взаимодействие | Вход через внешний провайдер |
| Можно ли отозвать? | Да, уничтожив сессию на сервере | Сложнее: пока не истёк, токен живёт, если нет blacklist | Да, можно отозвать у провайдера или разорвать связь |
| Кросс-доменно работает? | Неудобно, зависит от cookie policy и доменов | Да, удобно через заголовок Authorization | Да, потому что flow построен на redirect и back-channel |

## 27. Что на самом деле получилось по архитектуре

Текущая архитектура рабочая, но компромиссная:

- React получает JWT не напрямую при логине, а через `/api/me.php`
- PHP и FastAPI разделяют один общий секрет
- нет refresh token
- нет scopes
- нет revoke списка для JWT

Для учебной практики это нормальное решение, но в production обычно используют более зрелые готовые библиотеки и пакеты.

## 28. Три бага, которые Laravel-пакеты закрывают из коробки

### Баг 1. Хранение секретов прямо в коде

**Что за баг:**  
`SECRET_KEY`, `client_id`, `client_secret` легко оставить прямо в файлах.

**Чем опасен:**  
секрет может попасть в git, скриншоты, историю shell, PR или просто быть засвечен при отладке.

**Какой пакет/механизм решает:**  
Laravel в связке с `.env`, конфигами и экосистемой вроде Socialite / Sanctum / Passport позволяет хранить секреты вне кода и работать через централизованную конфигурацию.

---

### Баг 2. Ручная реализация OAuth flow

**Что за баг:**  
мы вручную собираем `state`, redirect, обмен `code -> access_token`, запрос профиля и связывание пользователя.

**Чем опасен:**  
легко допустить ошибку:

- забыть проверить `state`
- забыть `User-Agent`
- неверно обработать callback
- неправильно разобрать ответ провайдера

**Какой пакет решает:**  
Laravel Socialite закрывает типовой OAuth flow из коробки и сильно снижает риск ошибок в ручной реализации.

---

### Баг 3. Самодельный JWT-механизм без инфраструктуры отзыва и политик

**Что за баг:**  
мы вручную генерируем и проверяем JWT, но не реализуем:

- refresh token
- revoke/blacklist
- scopes/permissions
- ротацию ключей

**Чем опасен:**  
если токен утечёт, он будет жить до `exp`; также трудно централизованно управлять доступом.

**Какой пакет решает:**  
Laravel Passport даёт более полноценную OAuth2/JWT-инфраструктуру, а Laravel Sanctum удобно закрывает сценарии SPA и cookie/session auth без ручного бойлерплейта.
